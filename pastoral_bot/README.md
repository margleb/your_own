# Православный помощник

Независимый Telegram-сервис с тремя режимами: беседа, вопросы о вере и временная подготовка к исповеди. Доступен через текстовый бот и Telegram Mini App. Он явно представляется ИИ. Старый `main.py`, личная память, автономные workers и HTTP API личного приложения не используются. Существующие пользовательские изменения проекта сохраняются.

## Подготовка

Нужны Python 3.12+, отдельный бот в BotFather, отдельный ключ OpenRouter и PostgreSQL с pgvector. Библиотека и диалоги принадлежат отдельной базе. Не используйте личный Telegram-токен, базу `your_own` или её каталоги состояния.

```bash
python -m pip install -r pastoral_bot/requirements.txt
```

Для запуска профильных тестов установите `pastoral_bot/requirements-dev.txt`:
общие fixtures проекта также импортируют модули личного приложения.
Для VPS без sudo предусмотрено полностью отдельное развёртывание Docker:
[инструкция](deploy/README.md). Контейнеры не используют checkout или данные
работающего личного сервиса.
Для работающего экземпляра на FirstVDS есть [операторская памятка](deploy/FIRSTVDS.md).

Скопируйте `pastoral_bot/.env.example` в `/etc/pastoral-bot.env`, заполните значения и ограничьте доступ к файлу (`chmod 600`). Пароль в `PASTORAL_DATABASE_URL` должен быть URL-encoded. Сервис читает только переменные `PASTORAL_*`; личный `.env` автоматически не загружается. Для терминала экспортируйте эти переменные безопасным способом, без печати секретов.

При использовании OpenRouter отключите в отдельном аккаунте **Input & Output Logging** и **Use Inputs/Outputs**, проверьте отсутствие Broadcast destinations. Если журналирование нужно другим ключам, исключите ключ бота. `provider.zdr=true` ограничивает провайдеров inference; настройки журналирования самого OpenRouter существуют отдельно. Это условие нужно проверить в аккаунте перед публичным запуском: [журналирование](https://openrouter.ai/docs/guides/features/input-output-logging), [сбор данных](https://openrouter.ai/docs/guides/privacy/data-collection).

Для полностью отдельного PostgreSQL-кластера предусмотрен Compose. Заполните оба отдельных пароля; приложение использует роль `pastoral`, без superuser-прав:

```bash
docker compose --env-file /etc/pastoral-bot.env -f pastoral_bot/deploy/compose.yaml up -d db
python -m pastoral_bot init-db
python -m pastoral_bot doctor
```

`init-db` создаёт только новые таблицы; он не переносит старую историю. Для готового отдельного PostgreSQL администратор должен заранее установить расширение `vector`. Каталог `PASTORAL_STATE_DIR` должен принадлежать пользователю сервиса, с правами 0700.

## Telegram Mini App

Интерфейс в `pastoral_bot/miniapp` переносит утверждённый прототип Figma: три режима, беседа, проверяемые источники, редактируемая личная заметка и настройки. Он получает реальные ответы того же обработчика, использует общую историю, очередь, бюджет и отмену. Ответы приложения не публикуются в текстовом чате Telegram.

Сборка требует Node.js 22.12+:

```bash
cd pastoral_bot/miniapp
npm ci
npm test
npm run build
```

Docker собирает frontend автоматически. Для обычного Python-запуска сборка `miniapp/dist` должна уже существовать. Задайте `PASTORAL_WEB_ENABLED=true`, `PASTORAL_WEB_HOST=0.0.0.0`, `PASTORAL_WEB_PORT=8091` и `PASTORAL_WEB_PUBLIC_URL=https://bot-ams.margleb.ru/pastoral/`. HTTPS-прокси описан в [памятке FirstVDS](deploy/FIRSTVDS.md). При запуске бот настраивает кнопку меню «Открыть приложение», а `/start` добавляет такую же кнопку во вступление.

API принимает только проверенный Telegram `initData` в заголовке `Authorization: tma …`: HMAC, срок до двух часов и положительный подписанный идентификатор пользователя. `initDataUnsafe`, произвольный ID из тела и групповые запуски не дают доступа. Обычное открытие сайта показывает приглашение перейти в Telegram. Frontend не хранит авторизацию или заметки в localStorage/sessionStorage; сроки временного режима проверяются сервером и приложением. После истечения или перезапуска нужно явно начать подготовку заново.

`GET api/state`, `POST api/messages` и опрос `GET api/messages/{request_id}` используют относительные пути, пригодные для размещения под `/pastoral/`. Запросы управления `mode`, `new`, `stop`, `delete-history` проверяют текущую `expected_epoch`; удаление требует `confirm=true`. UUID сообщения обеспечивает повтор отправки без второй генерации. HTTP работает в процессе long polling, журналы доступа и журналы сырых ошибок HTTP отключены.

## Библиотека

Манифест `sources.json` фиксирует четыре источника и редакции. Новый Завет импортируется из выбранного Синодального FB2 с проверкой всех 27 книг, глав и стихов. Катехизис помечен как модернизированная редакция 2013 года. HTML-парсеры исключают навигацию и сохраняют расположение фрагментов.

Сначала получите проверяемую копию:

```bash
python -m pastoral_bot.import_sources preview --version 2026-10-03 --output /var/lib/pastoral-bot/corpus-preview.json
```

Просмотрите текст, редакции и адреса. После проверки передайте SHA256, выведенный preview:

```bash
python -m pastoral_bot.import_sources apply /var/lib/pastoral-bot/corpus-preview.json --approve REVIEWED_SHA256
python -m pastoral_bot doctor
```

Подтверждение относится к каноническому JSON bundle, включая тексты, редакции, указатели и URL. Повторный импорт той же версии идемпотентен; изменённый текст требует новой версии. Старые версии остаются неодобренными и не участвуют в ответах. Первый импорт загружает локальную модель embeddings в изолированный cache и считает векторы пакетами по 64. Новая редакция переиспользует векторы неизменённых публичных текстов того же источника. Если embeddings недоступны, библиотека использует русский полнотекстовый поиск; отсутствие подходящих источников явно сообщается пользователю.

Публичный запуск требует всех четырёх одобренных документов. Цитирование проверяется сервером, но соответствие церковному учению требует содержательной проверки ответов.

## Работа и конфиденциальность

```bash
python -m pastoral_bot run
```

Один long-poll consumer; PostgreSQL advisory lock исключает параллельный запуск сервиса с той же базой. Принимаются только личные текстовые сообщения, идентичность определяется числовым Telegram `from.id`. Callback привязан к текущей версии разговора. Состояние режима фиксируется до подтверждения кнопки Telegram.

- `/start`, `/help`, `/mode`: вступление и три режима.
- `/new`: новая тема; обычная память сохраняется.
- `/stop`: отмена генерации и очереди.
- `/privacy`: правила хранения.
- `/delete_history`: подтверждаемое удаление истории, поисковых фрагментов и текущих заданий.

По умолчанию — 10 ответов модели на человека в московские сутки, $5 общего бюджета модели, четыре одновременные генерации. Команды управления и заранее заданные пояснения о хранении данных и границах роли доступны без вызова модели. Максимальная стоимость первого вызова и одной попытки исправления резервируется до запроса. Ошибки, отмены и неизвестная стоимость учитываются консервативно; они не расходуют квоту успешно подготовленных ответов. Цена провайдера ограничена на уровне маршрутизации. Сервер и реклама в этот бюджет не входят.

Обычная история сохраняется до удаления. В контекст попадают только завершённые обмены: последние восемь текущей темы и максимум три подходящих обмена прежних тем того же пользователя. Будущие сообщения в очереди не попадают в ранний ответ.

Подготовка к исповеди хранит текст только в RAM. Таймаут — 30 минут бездействия, абсолютная длительность — два часа. Временные задания в очереди тоже истекают. Контекст после перезапуска исчезает; режим остаётся временным до явного переключения. Сообщения текстового бота остаются в облачной истории Telegram; беседы Mini App туда не отправляются. В обоих интерфейсах сообщения передаются модели через OpenRouter с ZDR; это не обещание абсолютной анонимности.

Журналы не содержат prompts, ответов, сырых Telegram updates, SQL-параметров или тел ошибок. Личный режим существующего LLM-клиента сохраняет прежнее поведение; `complete_private` использует безопасный отдельный контракт.

Длинные ответы делятся без потерь, с учётом UTF-16. После сбоя доставки модель не вызывается заново для уже готового ответа. Обычные готовые ответы восстанавливают доставку с подтверждённого фрагмента. При неопределённом сетевом исходе автоматическая повторная отправка не выполняется; exactly-once доставка Telegram не обещается.

## Проверка и запуск на сервере

```bash
python -m pytest tests/pastoral tests/test_llm_contract.py tests/telegram tests/test_call_log.py tests/test_lint.py -q
python -m pastoral_bot.evaluation --output /var/lib/pastoral-bot/evaluation-cases.json
```

В evaluation включены 60 русскоязычных сценариев. Для настоящих ответов модели создайте отдельную базу с `_eval` в имени, импортируйте туда проверенную библиотеку и задайте соответствующий `PASTORAL_DATABASE_URL`. Обязательно задайте `PASTORAL_BUDGET_DATABASE_URL`, указывающий на ту же базу бюджета, которую использует публичный бот (по умолчанию его обычная отдельная база `pastoral`). Так проверка не создаст вторую квоту $5; тексты синтетических сценариев останутся только в `_eval`:

```bash
python -m pastoral_bot.evaluation --run --output /var/lib/pastoral-bot/evaluation-report.json
```

CLI соблюдает тот же бюджет. Отчёт содержит только синтетические сценарии, ответы и использованные фрагменты источников. `format_passed` проверяет техническое прохождение; поле `review` остаётся `pending`. Перед рекламой вручную проверьте все ответы, точность цитат и поддержку утверждений источниками. Не считайте успешный JSON богословской проверкой.

Для systemd используйте файлы `deploy/pastoral-bot.service`, `pastoral-backup.service/.timer` и `pastoral-prune.service/.timer`. В примерах checkout расположен в `/opt/your_own`, пользователь ОС — `pastoral`, environment file — `/etc/pastoral-bot.env`. PostgreSQL client tools `pg_dump`/`pg_restore` должны соответствовать версии сервера. Ежедневный backup и независимая ежечасная очистка обеспечивают семидневное хранение.

Резервные копии создаются в `PASTORAL_STATE_DIR/backups`, шифруются Fernet и никогда не записываются открытым текстом. Сгенерируйте ключ один раз и храните отдельную защищённую копию. Журналы `deletions.jsonl` и `modes.jsonl` содержат только метаданные, находятся вне database snapshots и должны пережить восстановление. Без оригинальных журналов restore запрещён: иначе может восстановиться удалённая история или режим сохранения после временной беседы.

Снимок включает только таблицы `public.pastoral_*` и их индексы/последовательности. Администратор должен заранее установить `vector` в базе восстановления: расширение и другие административные объекты снимок не удаляет и не восстанавливает от имени ограниченной роли приложения.

Остановив бот, можно восстановить отдельную базу:

```bash
python -m pastoral_bot backup
python -m pastoral_bot restore /var/lib/pastoral-bot/backups/pastoral-TIMESTAMP.dump.enc --confirm-restore
```

После restore повторно применяются удаления и последние явные режимы, включая пользователей, появившихся после snapshot. Никогда не удаляйте журналы метаданных вместе с очищаемыми backups. Катастрофическая потеря этих файлов требует отдельного безопасного восстановления, а не запуска со старой обычной памятью.

## Telega.in

Перечислите разрешённые campaign ID в `PASTORAL_CAMPAIGNS`. Используйте отдельные ссылки `https://t.me/BOT_USERNAME?start=telega_prayers` для каждого размещения. Первый источник закрепляется; повторный `/start` его не меняет. Команда `python -m pastoral_bot metrics` показывает агрегаты стартов, первого ответа и возвращений по кампаниям. Содержание бесед не анализируется. Рекламные размещения сервис автоматически не покупает.

## Проверка реализации, 3 октября 2026

- Профильный набор: 351 тест прошёл, два PostgreSQL-теста пропускаются без отдельной тестовой DSN. PostgreSQL дополнительно проверен в временных изолированных базах, которые затем удалены.
- Полные четыре источника: 8964 фрагмента, успешный импорт в PostgreSQL, повторный импорт без изменений, проверка русского FTS и pgvector. При этой проверке полного импорта использовались детерминированные тестовые векторы.
- Настоящая модель MiniLM отдельно проверена на CPU: 384 конечных компоненты, совпадение одиночного и пакетного вызовов, отсутствие текстов запросов в журнале. Публичные веса находятся в изолированном cache.
- Полный набор старого приложения: 1403 теста прошли, три пропущены, два существующих сбоя воспроизведены и с исходными транспортными модулями: `test_auth_coverage` (список публичных маршрутов) и `test_people` (формат имени в промпте). Пользовательские изменения этих частей сохранены.
- Живые Telegram/OpenRouter вызовы и содержательная проверка 60 ответов ещё требуют новых credentials и запуска evaluation. Технические тесты не заменяют эту проверку.
